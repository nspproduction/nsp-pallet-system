## 1. เป้าหมาย

1. บันทึกการเบิกและคืนพาเลทระหว่าง **คลังพาเลท** กับแผนกต่าง ๆ ให้ตรวจสอบย้อนหลังได้ทุกรายการ
2. รู้ยอดพาเลท **ในคลัง** ณ ปัจจุบัน แยกตามประเภทและสภาพ
3. รู้ว่าแต่ละแผนก/บุคคล เบิกและคืนไปเท่าไร
4. ควบคุมด้วยลำดับการอนุมัติที่กำหนดได้รายแผนก และช่วงเวลาทำรายการ
5. มี Dashboard สำหรับ monitor ภาพรวมและเชิงลึก

## 2. ขอบเขต

### In scope (v1)

- Web app แบบ responsive ใช้ได้ทุกอุปกรณ์ (มือถือ, tablet, desktop)
- Requester: เบิก และคืน
- Pallet Manager: รับพาเลทใหม่เข้าคลัง, บันทึกผลซ่อม, ตัดจำหน่าย
- Admin: ปรับยอด และงานหลังบ้าน
- Approval route ที่กำหนดได้รายแผนก
- ช่วงเวลาทำรายการ และคำขอด่วนนอกเวลา
- ระบบสมาชิก username/password + email, การอนุมัติสมาชิกโดย admin
- แจ้งเตือนทาง **email** และในระบบ (in-app)
- Dashboard + Export Excel และ Audit log

### Out of scope (v1)

- **ติดตามยอดพาเลทที่อยู่นอกคลัง** (ที่แผนก, ระหว่างแผนก, ที่ลูกค้า) — ระบบรู้แค่ยอดเบิก/คืนของแต่ละแผนก
- การส่งต่อพาเลทระหว่างแผนก, การส่งพาเลทให้ลูกค้า และรับคืนจากลูกค้า (ถ้าพาเลทจากลูกค้าเข้าคลัง ให้แผนกจ่ายสินค้าทำคำขอ **คืน** ตามปกติ)
- ติดตามพาเลทรายตัว (serial / barcode / RFID) — นับเป็น **จำนวนตามประเภท**
- แจ้งเตือนผ่าน LINE / SMS
- เชื่อมต่อ ERP หรือระบบอื่น
- Mobile native app

## 3. คำศัพท์

| คำ                     | ความหมาย                                                                    |
| ---------------------- | --------------------------------------------------------------------------- |
| คลังพาเลท (Warehouse)  | จุดเก็บพาเลทกลาง ไม่ใช่คลังของพัสดุ — เป็น **ที่เดียวที่ระบบติดตามยอด**     |
| พัสดุ (Supply)         | หน่วยงานที่มีพาเลทใหม่ เป็นแหล่งที่มาของพาเลทใหม่เข้าคลัง                   |
| สภาพ (Condition)       | `GOOD` ดี, `PENDING_REPAIR` รอซ่อม, `DAMAGED` เสีย (รอตัดจำหน่าย)           |
| ตัดจำหน่าย (Write-off) | นำพาเลทสภาพเสียออกจากคลังอย่างถาวร                                          |
| Request                | คำขอหนึ่งรายการ: **1 สภาพ** และมีได้หลายประเภทพาเลท (item = ประเภท × จำนวน) |
| คำขอด่วน (Urgent)      | คำขอที่ส่งนอกช่วงเวลาทำรายการ                                               |
| Ledger                 | บันทึกการเคลื่อนไหวของยอดในคลัง แก้ไขหรือลบไม่ได้                           |

## 4. โครงสร้างองค์กร

- แผนกเริ่มต้น: ผลิต, พัสดุ, จ่ายสินค้า, QA, RD และแผนกอื่น ๆ ที่ admin เพิ่มได้
- แผนกมี **section ย่อย** ได้ (เช่น ผลิต → alpha, beta, mixer, packer) ออกแบบเป็นลำดับชั้น (`parentId`)
- User สังกัด 1 แผนกหรือ 1 section
- **ไม่มีการเลือก location ในคำขอ** — แผนก/section ของคำขอคือแผนก/section ของผู้ร้องขอ ณ เวลาที่สร้างคำขอ (บันทึกค่าไว้กับคำขอ ถ้าภายหลัง user ย้ายแผนก ประวัติเดิมไม่เปลี่ยน)
- Approval route และสถิติ Dashboard ใช้แผนกระดับบน หรือ section 🟡 (Q11)

## 5. Roles และสิทธิ์

| Role             | สิทธิ์                                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `REQUESTER`      | สร้างคำขอเบิก/คืนในนามแผนกตัวเอง, ยกเลิกได้เฉพาะก่อนมีการอนุมัติขั้นแรก, ดูประวัติของแผนกตัวเอง                                               |
| `DEPT_APPROVER`  | อนุมัติ/ปฏิเสธคำขอของแผนกตัวเองตามขั้นที่ได้รับมอบหมายใน route                                                                                |
| `PALLET_MANAGER` | อนุมัติขั้นสุดท้ายทุกคำขอเบิก/คืน, แก้ไขคำขอ (มี log), รับพาเลทใหม่, บันทึกผลซ่อม, ตัดจำหน่าย                                                 |
| `VIEWER` 🟡      | ดู Dashboard อย่างเดียว (สำหรับผู้บริหาร)                                                                                                     |
| `ADMIN`          | จัดการ user (อนุมัติการสมัคร, กำหนด role/แผนก), แผนก/section, ประเภทพาเลท, approval route, ช่วงเวลาทำรายการ, ปรับยอด, สร้าง/อนุมัติคำขอแทนได้ |
| `SUPER_ADMIN`    | ทุกอย่างของ ADMIN + จัดการ admin คนอื่น, ตั้งค่าระบบ (เช่น ตั้งค่า email), ดู audit log ทั้งหมด                                               |

กฎ:

- User มีได้หลาย role (เช่น REQUESTER + DEPT_APPROVER)
- **ห้ามอนุมัติคำขอที่ตัวเองสร้าง** และห้ามคนเดียวอนุมัติ 2 ขั้นในคำขอเดียวกัน
- ทุกการกระทำแทนผู้อื่นของ admin ต้องบันทึกใน audit log ว่าใครทำ

## 6. ประเภทธุรกรรม

| Type                     | ผล ต่อยอดในคลัง                          | สภาพ                                          | ผู้สร้าง       | ต้องผ่าน approval route        |
| ------------------------ | ---------------------------------------- | --------------------------------------------- | -------------- | ------------------------------ |
| `ISSUE` เบิก             | GOOD −                                   | `GOOD` เท่านั้น                               | Requester      | ✅ แผนก → Pallet Manager       |
| `RETURN` คืน             | สภาพที่ระบุ +                            | เลือก 1 สภาพ: GOOD / PENDING_REPAIR / DAMAGED | Requester      | ✅ แผนก → Pallet Manager       |
| `NEW_STOCK` รับพาเลทใหม่ | GOOD +                                   | `GOOD`                                        | Pallet Manager | ❌ บันทึกแล้วมีผลทันที 🟡 (Q7) |
| `REPAIR_RESULT` ผลซ่อม   | PENDING_REPAIR − แล้ว GOOD + / DAMAGED + | PENDING_REPAIR → GOOD หรือ DAMAGED            | Pallet Manager | ❌                             |
| `WRITE_OFF` ตัดจำหน่าย   | DAMAGED −                                | `DAMAGED`                                     | Pallet Manager | ❌                             |
| `ADJUSTMENT` ปรับยอด     | + หรือ −                                 | ใดก็ได้                                       | Admin          | ❌ ต้องมีเหตุผล                |

หมายเหตุ:

- คืนพาเลทหลายสภาพพร้อมกัน → requester สร้างคำขอแยกตามสภาพ (หน้าจอควรมีปุ่ม "สร้างคำขอคืนอีกสภาพ" ที่คัดลอกข้อมูลเดิมไปให้)
- `REPAIR_RESULT` ทำได้ครั้งละหลายประเภทพาเลท โดยระบุจำนวนซ่อมได้ (→ GOOD) และซ่อมไม่ได้ (→ DAMAGED) รวมกันต้องไม่เกินยอด PENDING_REPAIR

### ตัวอย่างการใช้งานจริง

- alpha เบิก 20 → ใช้ไม่หมด → alpha คืน 5 (ดี)
- alpha เบิก 20 → พาเลทไหลไปที่ mixer → mixer คืน 15 (ดี) และคืน 5 (รอซ่อม) เป็น 2 คำขอ
- พาเลทที่ลูกค้านำมาคืน → แผนกจ่ายสินค้าทำคำขอคืนเข้าคลัง

## 7. Approval Workflow (เฉพาะ ISSUE / RETURN)

### 7.1 Approval Route

- Admin กำหนด route ได้ **รายแผนก × ประเภทคำขอ (ISSUE / RETURN)** (เช่น ผลิต มี 2 ขั้น, RD มี 1 ขั้น)
- แต่ละขั้น (step) มีลำดับ (`order`) และกำหนดผู้อนุมัติเป็นกลุ่ม user ได้ (ใครในกลุ่มอนุมัติก็ได้ 1 คน)
- ขั้นสุดท้ายของทุก route คือ `PALLET_MANAGER` เสมอ (ระบบเติมให้อัตโนมัติ admin ลบไม่ได้)
- ถ้าแผนกไม่มี route ที่ตั้งไว้ → ห้ามส่งคำขอ และแสดงข้อความให้ติดต่อ admin
- เมื่อส่งคำขอ ระบบ **snapshot route** ไว้กับคำขอ การแก้ route ภายหลังไม่กระทบคำขอที่ค้างอยู่

### 7.2 สถานะคำขอ

```
DRAFT → PENDING_DEPT (step 1..n) → PENDING_WAREHOUSE → COMPLETED
                 ↓                         ↓
             REJECTED                  REJECTED
CANCELLED (requester ยกเลิกได้ก่อนการอนุมัติขั้นแรก)
```

- `COMPLETED` = Pallet Manager อนุมัติแล้ว และ **ยอดในคลังเปลี่ยนจริงแล้ว** (ยอดเปลี่ยนเฉพาะตอนนี้เท่านั้น)
- Reject ทุกขั้นต้องระบุเหตุผล คำขอที่ถูก reject ถือว่าจบ requester ต้องสร้างใหม่ (มีปุ่ม "คัดลอกเป็นคำขอใหม่")

### 7.3 การแก้ไขคำขอโดย Pallet Manager (🟡 Q1 — ร่างตามคำแนะนำ รอยืนยัน)

Pallet Manager ทำได้ 2 ทาง:

1. **Reject** — เมื่อคำขอผิดในสาระสำคัญ
2. **แก้ไขแล้วอนุมัติ** — เมื่อของจริงต่างจากที่แจ้ง (จำนวน, ประเภทพาเลท, สภาพ) โดย:
   - ต้องกรอกเหตุผลการแก้ไข
   - ระบบเก็บ **revision** ทุกครั้ง (ค่าเดิม → ค่าใหม่, ใคร, เมื่อไร, เหตุผล) แก้หรือลบ revision ไม่ได้
   - หน้ารายละเอียดคำขอแสดงป้าย "แก้ไขโดยคลัง" และแสดงค่าเดิมเทียบค่าใหม่
   - แจ้งเตือน (email + in-app) ไปยัง requester และ approver ของแผนกที่อนุมัติคำขอนี้
   - Dashboard มีรายงาน "คำขอที่ถูกแก้ไข" รายแผนก

## 8. ช่วงเวลาทำรายการและคำขอด่วน

- Admin ตั้งช่วงเวลาทำรายการได้ **รายวันในสัปดาห์** วันละหลายช่วง เช่น จ–ส 09:00–11:30 และ 13:00–15:00, อาทิตย์ ไม่เปิด
- ใช้เวลา Asia/Bangkok และตรวจจาก **เวลาที่กดส่งคำขอ** (ฝั่ง server ไม่ใช่เวลาเครื่องผู้ใช้)
- ในช่วงเวลา → ส่งคำขอปกติ
- นอกช่วงเวลา → ส่งแบบปกติไม่ได้ แต่ส่งเป็น **คำขอด่วน** ได้ โดย:
  - ต้องกรอกเหตุผลความจำเป็น
  - คำขอมีป้าย "ด่วน" ชัดเจนในทุกหน้า และแสดงบนสุดของคิวอนุมัติ
  - ผู้อนุมัติได้รับ email ที่ระบุว่าเป็นคำขอด่วน
  - Dashboard นับจำนวนคำขอด่วนรายแผนก
- การอนุมัติทำได้ทุกเวลา ไม่ถูกจำกัดด้วยช่วงเวลา
- ช่วงเวลาใช้กับคำขอทั้งเบิกและคืน 🟡 (Q12) และวันหยุดพิเศษของบริษัท 🟡 (Q13)

## 9. กฎทางธุรกิจ (Business Rules)

- **BR-1** ยอดในคลังของทุก ประเภท × สภาพ ต้องไม่ติดลบ
- **BR-2** `ISSUE` ตรวจยอด GOOD คงเหลือ 2 จังหวะ: ตอนส่งคำขอ (เตือน แต่ส่งได้) และตอน Pallet Manager อนุมัติ (บังคับ — ยอดไม่พอ อนุมัติไม่ได้)
- **BR-3** `RETURN` **ไม่ถูกบล็อก** แม้ยอดคืนสะสมของแผนกจะเกินยอดเบิกสะสม (เพราะช่วงแรกพาเลทกระจายอยู่ตามแผนกโดยไม่มีบันทึก) แต่ต้อง **แสดงข้อความแจ้ง** เช่น "แผนกนี้คืนเกินยอดเบิกสะสม 40 ใบ" ให้ requester เห็นตอนส่ง และ approver/Pallet Manager เห็นในหน้าอนุมัติ
- **BR-4** ทุกคำขอมี 1 สภาพ, อย่างน้อย 1 item, ประเภทพาเลทห้ามซ้ำในคำขอเดียว, จำนวนเป็นจำนวนเต็มบวก
- **BR-5** การเปลี่ยนยอดทุกครั้งต้องเขียน ledger และอัปเดตยอดคงเหลือ **ใน DB transaction เดียวกัน**
- **BR-6** Ledger เป็น append-only ถ้าผิดให้แก้ด้วย `ADJUSTMENT` เท่านั้น
- **BR-7** `ADJUSTMENT` และ `WRITE_OFF` ต้องมีเหตุผลเสมอ
- **BR-8** User ที่สถานะไม่ใช่ `ACTIVE` เข้าระบบไม่ได้
- **BR-9** การปิดใช้งานแผนก/ประเภทพาเลท/user ทำได้แบบ soft-disable เท่านั้น (ห้ามลบถ้ามีประวัติ)
- **BR-10** คำขอปกติส่งได้เฉพาะในช่วงเวลาทำรายการ นอกเวลาต้องเป็นคำขอด่วนพร้อมเหตุผล

## 10. ระบบสมาชิก

- สมัครด้วย: username, **email**, password, ชื่อ-นามสกุล, รหัสพนักงาน, แผนก/section ที่ขอ, เบอร์ติดต่อ
- username และ email ห้ามซ้ำ; login ด้วย username + password
- สถานะ: `PENDING` → (admin ตรวจสอบ กำหนด role + แผนก/section แล้วอนุมัติ) → `ACTIVE` / หรือ `REJECTED`; ภายหลังปิดได้เป็น `DISABLED`
- เมื่อสมัคร → email แจ้ง admin; เมื่ออนุมัติหรือปฏิเสธ → email แจ้งผู้สมัคร
- Password ขั้นต่ำ 8 ตัว เก็บแบบ hash (argon2 หรือ bcrypt)
- **ลืมรหัสผ่าน** ด้วยตัวเองผ่านลิงก์ทาง email (ลิงก์หมดอายุใน 30 นาที ใช้ได้ครั้งเดียว) และ admin รีเซ็ตให้ได้
- Login ผิดติดกัน 5 ครั้ง → ล็อก 15 นาที
- วิธีทำ auth 🟡 (Q3)

## 11. การแจ้งเตือน

ทุกเหตุการณ์ส่งทั้ง **email และ in-app** ยกเว้นระบุไว้

| เหตุการณ์                     | ผู้รับ                                                 |
| ----------------------------- | ------------------------------------------------------ |
| คำขอถึงขั้นของตน              | ผู้อนุมัติในขั้นนั้นทุกคน                              |
| คำขอถูกอนุมัติครบ (COMPLETED) | Requester                                              |
| คำขอถูกปฏิเสธ                 | Requester (+ approver ขั้นก่อนหน้า เฉพาะ in-app)       |
| คำขอถูกแก้ไขโดยคลัง           | Requester + approver แผนกที่อนุมัติแล้ว                |
| มีผู้สมัครใหม่                | Admin ทุกคน                                            |
| ผลการสมัคร                    | ผู้สมัคร                                               |
| ยอด GOOD ต่ำกว่าจุดสั่งเพิ่ม  | Pallet Manager + Admin (ไม่เกินวันละ 1 ครั้งต่อประเภท) |

- การส่ง email ต้องไม่ทำให้การอนุมัติล้มเหลว (ส่งไม่สำเร็จ → บันทึก error และลองใหม่ แต่การอนุมัติยังสำเร็จ)
- Email ภาษาไทย มีลิงก์ตรงไปหน้าคำขอ

## 12. หน้าจอ

ทุกหน้าเป็น responsive (มือถือ → desktop), ฟอนต์ Noto Sans Thai

### ผู้ใช้ทั่วไป

- **หน้าแรก**: สถานะช่วงเวลาทำรายการตอนนี้ (เปิด/ปิด, ปิดเมื่อไร), คำขอล่าสุดของฉัน, ปุ่มลัด เบิก / คืน, ยอดเบิก/คืนของแผนกเดือนนี้
- **สร้างคำขอ**: เลือก เบิก/คืน → (คืน: เลือกสภาพ) → เพิ่ม item (ประเภทพาเลท, จำนวน) → หมายเหตุ → ส่ง; นอกเวลาแสดงตัวเลือกคำขอด่วน
- **คำขอของฉัน**: รายการ + filter สถานะ; หน้ารายละเอียดมี timeline การอนุมัติและ revision
- **รออนุมัติ** (approver / Pallet Manager): คำขอด่วนอยู่บนสุด, อนุมัติ/ปฏิเสธ/แก้ไข, แสดงข้อความเตือนตาม BR-2 / BR-3
- **แจ้งเตือน**: in-app notification
- **โปรไฟล์**: แก้ email/เบอร์, เปลี่ยนรหัสผ่าน

### Pallet Manager

- คิวรออนุมัติ, ยอดคลังปัจจุบัน, รับพาเลทใหม่, บันทึกผลซ่อม, ตัดจำหน่าย, ประวัติการเคลื่อนไหวในคลัง

### Admin

- อนุมัติสมาชิก, จัดการ user / role, แผนก / section, ประเภทพาเลท, approval route, ช่วงเวลาทำรายการ, ปรับยอด, audit log
- SUPER_ADMIN เท่านั้น: จัดการ admin, ตั้งค่าระบบ

### Dashboard

- **ยอดในคลัง**: รายประเภท แยก ดี / รอซ่อม / เสียรอตัดจำหน่าย และรวม
- **การเคลื่อนไหวของคลัง** ตามช่วงเวลา: รับใหม่, เบิกออก, คืนเข้า (แยกสภาพ), ซ่อมได้/ซ่อมไม่ได้, ตัดจำหน่าย, ปรับยอด
- **รายแผนก/section**: ยอดเบิก, ยอดคืน (แยกสภาพ), ส่วนต่างเบิก−คืน (ใช้ดูแนวโน้มเท่านั้น ไม่ใช่ยอดคงเหลือจริง), สัดส่วนคืนสภาพเสีย/รอซ่อม
- **รายคน**: จำนวนคำขอ, จำนวนพาเลทที่เบิก/คืน
- **คุณภาพการซ่อม**: อัตราซ่อมได้ต่อประเภทพาเลท
- **การอนุมัติ**: คำขอค้างแต่ละขั้น, เวลาอนุมัติเฉลี่ย, จำนวนคำขอที่ถูกแก้ไข/ปฏิเสธ, จำนวนคำขอด่วน
- **แนวโน้ม**: กราฟรายวัน/สัปดาห์/เดือน
- **แจ้งเตือน**: ยอด GOOD ต่ำกว่าจุดสั่งเพิ่ม
- Filter: ช่วงวันที่, แผนก/section, ประเภทพาเลท, สภาพ
- **Export Excel (.xlsx)** ทุกตารางบน Dashboard ตาม filter ที่เลือก; หัวคอลัมน์ภาษาไทย, ตัวเลขเป็นตัวเลขจริง (ไม่ใช่ข้อความ), วันที่เป็นเวลาไทย

## 13. Data Model (ร่าง — ชื่อ field ปรับได้ แต่ concept ต้องครบ)

     status[PENDING|ACTIVE|REJECTED|DISABLED], departmentId?, roles[], createdAt)

                                                          // append-only ledger ของคลัง

## 15. Acceptance Criteria (ต้องมี test ครอบ)

- **AC-1** คลังมี GOOD ประเภท A = 10; alpha ขอเบิก 12 → ส่งได้แต่มีคำเตือน; Pallet Manager อนุมัติไม่ได้ ระบบแจ้งยอดไม่พอ ยอดไม่เปลี่ยน
- **AC-2** ผลิตตั้ง route 2 ขั้น; requester ส่งคำขอ → แจ้งเตือน (email + in-app) เฉพาะ approver ขั้น 1; ขั้น 1 อนุมัติ → แจ้งขั้น 2; ขั้น 2 อนุมัติ → `PENDING_WAREHOUSE`
- **AC-3** RD ตั้ง route 1 ขั้น; หลัง approver RD อนุมัติ → `PENDING_WAREHOUSE` ทันที
- **AC-4** User ที่เป็นทั้ง requester และ approver ไม่เห็นปุ่มอนุมัติคำขอของตัวเอง และเรียก API ตรงได้ 403
- **AC-5** mixer คืน (รอซ่อม) ประเภท A 5 + ประเภท B 3 → หลังอนุมัติ คลัง PENDING_REPAIR A +5, B +3 และมี ledger 2 แถวที่อ้าง departmentId ของ mixer
- **AC-6** แผนก X เบิกสะสม 10 แล้วส่งคำขอคืน 50 → ส่งได้ มีข้อความ "คืนเกินยอดเบิกสะสม 40" ทั้งหน้าส่งและหน้าอนุมัติ, อนุมัติได้ตามปกติ
- **AC-7** Pallet Manager แก้คำขอคืนจาก 10 เป็น 8 พร้อมเหตุผล → มี revision 1 รายการ, requester ได้รับ email, หน้าคำขอแสดงค่าเดิมเทียบค่าใหม่, ยอดคลังเพิ่ม 8
- **AC-8** บันทึกผลซ่อม A: รอซ่อม 10 → ซ่อมได้ 8 + ซ่อมไม่ได้ 2 → PENDING_REPAIR −10, GOOD +8, DAMAGED +2; ระบุรวมเกินยอดรอซ่อม → บันทึกไม่ได้
- **AC-9** อนุมัติขั้นสุดท้าย 2 คำขอเบิกพร้อมกันที่รวมกันเกินยอดคงเหลือ → สำเร็จ 1 คำขอ ยอดไม่ติดลบ
- **AC-10** เวลาทำรายการ จ–ส 09:00–11:30: ส่งคำขอปกติวันจันทร์ 10:00 ได้; วันจันทร์ 12:00 หรือวันอาทิตย์ ส่งปกติไม่ได้ แต่ส่งเป็นคำขอด่วนได้เมื่อกรอกเหตุผล
- **AC-11** User ที่สมัครใหม่ login ได้ข้อความ "รอการอนุมัติ" จนกว่า admin จะอนุมัติ; อนุมัติแล้วได้รับ email
- **AC-12** Admin แก้ route ผลิตจาก 2 เป็น 3 ขั้น → คำขอที่ค้างอยู่ยังใช้ 2 ขั้นเดิม
- **AC-13** ระบบส่ง email ล้มเหลว → การอนุมัติยังสำเร็จ และ email อยู่ใน outbox สถานะ FAILED พร้อม error
- **AC-14** ยอดในคลังแต่ละ ประเภท × สภาพ = ผลรวม `quantityDelta` ใน ledger ทั้งหมด (ตรวจด้วย test)
- **AC-15** Export Excel จาก Dashboard ได้ไฟล์ .xlsx ที่ตัวเลขตรงกับที่แสดงบนหน้าจอตาม filter
